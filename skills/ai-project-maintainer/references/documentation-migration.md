# 文档整理与迁移

## 触发条件

仅当用户明确要求“整理维护文档”“统一文档目录”“迁移 Markdown 文档”或等价命令时使用本路径。普通 Bug 修复、界面样式调整、新增功能和一般维护不触发全项目扫描。

## 目标目录判定

1. 确认项目根、用户未提交改动、嵌套项目边界和排除项。
2. 优先复用项目已有且实际承载维护文档的规范目录：`文档/`、`docs/`、`documentation/` 或项目已明确约定的其他目录。
3. 如果不存在规范文档目录，建立统一的 `文档/` 目录。
4. 已在规范目录中的文件保持原位；已有规范结构时只整理新增或遗漏文档，不重复迁移。
5. 根目录控制文件是否保留在根目录，按项目工具约定判定；`AGENTS.md`、`CLAUDE.md`、`README.md` 等被工具要求从根读取的文件不得仅为整洁而移动。

## 扫描与分类

在用户明确授权的整理阶段扫描项目内 Markdown 文件，排除 `.git`、依赖、vendor、构建输出、缓存、生成目录、二进制、媒体、密钥和嵌套项目（除非明确包含）。分类记录至少包含：

- 文件原路径和目标路径；
- 文档类型（架构、Bug 历史、维护指南、发布说明、贡献说明或其他）；
- 是否已在规范目录；
- 是否需要移动、合并或只修复引用；
- 引用消费者和验证命令。

不得删除有内容的文档，不得覆盖同名文件，不得把业务源码或用户文档误判为维护记录。冲突、归属不明或工具要求不明时停止该文件并报告，不猜测合并。

## 迁移与引用

迁移前记录 Git 状态、文件清单、引用命中和路径基线。按批次移动文件，再使用结构化路径处理修复 Markdown 链接、图片链接、目录索引、配置、脚本和源码中的文档路径；不要用无边界的全局字符串替换破坏业务内容。新目录内的相对链接按新位置重新计算。

迁移后检查所有被迁移文件的引用、所有已知消费者和项目自有索引。发现新的规范目录结构后，停止全量迁移，只补遗漏文档和引用。重复执行同一整理命令必须是幂等的：已规范文件不再移动，已正确引用不再改写。

## 后续写入规则

整理完成后，在阶段报告中记录规范文档目录。后续新增的 `ARCHITECTURE.md`、`BUG_HISTORY.md`、维护记录、发布说明和相关 Markdown 默认直接写入该目录；根目录保留工具明确要求的控制文档。若项目结构约定变化，先更新架构记录和索引，再采用新的目录。

## 验证顺序

1. 迁移前后文件清单和 Git diff 对比；
2. Markdown 相对链接、索引引用和已知文本路径检查；
3. 项目提供的文档/索引健康检查；
4. 受影响功能的最小测试或文档构建检查；
5. 重复运行整理分析，确认无待迁移文件和无重复移动；
6. 报告迁移清单、跳过清单、引用修复、冲突/未处理项和实际验证结果。

未完成引用修复、冲突文件或不可用检查必须单独标为 `NOT_RUN`、`NOT_AVAILABLE` 或 `BLOCKED`，不能以“目录已整洁”代替验证。
