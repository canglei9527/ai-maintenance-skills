# 快速路径

## 只读路径

用于解释、审查、诊断、符号查找、日志读取和状态报告（用户未请求编辑）。

1. 确认 `project_root`、`target_anchor`、范围、排除项和适用的 `AGENTS.md`，不扫描父工作空间。
2. 读取浅层包/构建/测试/启动元数据和 Git 状态；优先从 `ai-context/INDEX.md` 按故障现象定位功能目录，并逐级读取 `ai-context/<项目相对目录>/INDEX.md`，直到选定第一个实现文件；最多跟踪一个相关架构主题和一个 Bug 主题。若项目提供索引健康检查，先读取 `VALID` / `UNRESOLVED` / `STALE_REVIEW` 结果：`UNRESOLVED` 路由回退到定向搜索，`STALE_REVIEW` 仅要求用当前源码复核，不自动改写索引。
3. 读取目标证据：命名的文件或精确符号/错误、最小相关配置、按需读取一个项目自有调用方/被调方，以及最小测试或复现。任务意图、操作边界和权威测试命令以审核后的 Markdown 索引为准；调用者、被调用者、继承、引用和影响范围使用 `rg`、语言服务器、编译器或可选代码图工具获取，并按当前源码验证。
4. 陈述证据、可能原因、替代方案和未验证边界。不得修改源码、添加测试、写 Bug 或架构记录、移动文件、创建分支、更新索引或创建备份。

"审查这个结构"在没有明确移动/重构请求时保持只读。路径或上传文本是证据，不是写入授权。

## 普通变更路径

用于 Bug 修复、聚焦功能、配置调整、行为变更或本地测试更新（不需要移动所有权）。

1. 记录根目录、锚点、范围、用户改动、当前行为、期望行为、复现和可测试假设；若存在 `ai-context/INDEX.md`，先按现象→功能目录→局部索引定位目标。
2. 导航缺失或已失真时，为写入任务建立/修正根索引和必要的多级目录索引，再仅读取目标、按需读取一个项目自有依赖/调用方、使用的配置/数据和最小相关测试。若健康检查报告 `UNRESOLVED`，先通过定向搜索确认当前入口再更新对应路由；`STALE_REVIEW` 只触发复核，不因提交或日期变化自动重写仍正确的索引。默认上限：50 search hits、12 candidate files、one dependency hop。
3. 仅在以下情况扩展一层：精确符号有多个真实调用方、边界跨包/进程/服务/数据库/浏览器、配置有已证实的覆盖、共享契约变更，或测试/启动发现外部原因。记录理由和新边界。
4. **修复和配置调整**：做最小兼容修改。保留公共行为、有用注释、命名、项目约定和无关的脏改动；不格式化或重命名无关代码，不升级依赖，不把任务转为结构工作。

   **新增或扩展功能必须同步更新架构文档**：这包括新增界面、页面、组件、交互流程和用户可见功能。同步更新受影响目录最近一级的 `ai-context/INDEX.md`；项目没有可用架构文档时，创建或补齐根目录 `ARCHITECTURE.md`，并登记新入口、职责、数据/接口边界和聚焦验证。普通 Bug 修复和纯样式调整不触发这条架构更新门。

   **设计改进和体验优化**：当用户明确要求"现代化界面"、"改进用户体验"、"优化交互流程"或类似设计改进时，最小改动原则**不适用于布局、信息架构和交互模式**。表层装饰（换配色、加动画）在没有解决布局和空间利用问题时无法达成现代化目标。此类需求允许：
   - 重新设计信息层级和布局结构（双栏改三栏、列表改卡片流）
   - 优化空间利用和信息密度（压缩工具栏、内联操作按钮）
   - 改进交互流程和状态可见性（减少点击层级、预览增强）
   - 调整视觉层次表达方式（字重、间距、分组代替颜色块）

   设计改进仍需保持向后兼容的数据格式、API 契约和核心功能行为，但 UI 组件结构和样式架构可以重构。
5. 添加或更新最小有意义的回归测试。新增文件、目录、职责、公共入口或稳定故障路由时自动更新最近一级 `ai-context` 索引；只改实现细节时不改索引。仅在项目有此约定时为已确认缺陷更新 Bug 记录。
6. 先运行聚焦测试，再运行变更边界所需的语法/类型/格式/构建/启动检查。分开报告行为、结构、环境和未运行检查。

## 维护性检查点

A 900-line target does not require a prior refactor。在最小兼容修改就地完成聚焦修复，添加聚焦回归测试，不在无结构授权时提取无关内容。

在完成对超过 400 行手写文件、超过 200 行入口/UI/控制器/facade，或在可用 Git 证据中显示累积补丁历史的文件的任何变更前，检查变更边界是否出现以下信号：

- 文件有多个独立的变更原因或多个用户工作流；
- UI 构建、状态转换、进程或持久化 I/O、解析、配置、本地化混在一个类或模块中；
- 同一功能在同一所有者中需要协同编辑控件、状态、回调、字符串和测试；
- 顶层定义、公共入口或直接依赖形成可独立测试的分组；
- 最近重复的提交或当前改动在同一个超大所有者上扩展。

若无信号被支持，报告文件为大但内聚并说明证据。若有一个或多个信号被支持，先完成请求的行为，然后在完成报告的"未完成与风险"字段中简要标注 `ACCUMULATING_STRUCTURAL_DEBT`，列出具体触发信号和候选所有者——无需展开完整职责图，不中断当前修复流程，不单独询问结构授权（除非用户在当前请求中明确提及结构问题）。不将发现静默降级为"文件较大"。

当用户要求让项目更易维护、停止补丁堆积、解决 God Class 或修复结构问题本身时，该语言是结构意图，路由到 `STRUCTURAL_CHANGE`，不得用另一个聚焦补丁加模糊的未来重构注释来回答。

## 每轮读取与搜索预算

普通 Bug 修复每一轮最多打开 2–3 个文件；每个文件只读取目标方法、调用点或报错附近的局部行，默认前后各约 40 行。只有当前证据证明调用链跨边界，才进入下一轮并重新说明扩展理由。不要为了建立完整项目地图而读取 500 行以上的大文件，也不要把大型测试文件当作整体阅读对象。

搜索必须从精确路径、符号、错误文本或测试名称开始，并限定到单文件或单个模块。禁止一次 `rg` 覆盖多个产品模块、测试目录和 Web/Android 等无关边界；大型 JSON、书源数据、构建输出和生成目录默认排除。达到 50 个命中、8 KB 输出或发现首个可验证根因时停止搜索，先验证根因，不继续收集背景。确认规范实现文件和首个可验证根因后停止扩展，不做全量调用链扩展；只有证据显示跨模块时才按一跳依赖扩展。

未跟踪文件没有可比较的 Git 基线。禁止对未跟踪大文件执行完整 `git diff --no-index` 或重复输出整个文件；使用定向 `Read`、精确符号搜索或小范围临时比较，只查看验收所需片段。任何已经获得的文件内容不得为了“确认上下文”重复完整读取，除非文件时间戳或工作区状态证明它在工具调用之间发生变化。

## 搜索与读取限制

从精确路径、函数、类、路由、命令、配置键、事件、错误文本、失败测试或堆栈位置开始搜索。在每个深度排除 `.git`、依赖、vendor、构建输出、缓存、生成文件、二进制文件、媒体、密钥和无关兄弟项目。除非明确包含，否则在嵌套项目标记处停止。

默认限制是审查辅助手段：50 个搜索命中、12 个候选文件、一跳项目自有依赖和聚焦读取路径。不得将其作为普通变更的自动失败条件，也不得对普通变更使用全面扫描。仅凭证据扩展；全面扫描用于明确审计、清单、依赖检查或结构工作。

## 执行收敛与代理边界

把一次用户消息视为一个执行阶段，而不是全部 backlog。开始写入前记录四项：

- 当前目标：一个可复现故障或一个明确变更，不把“之后还要做”的独立事项并入当前阶段；
- 文件组：实现、最小测试和必要配置的有界集合；共享文件若服务多个工作流，先由主代理串行处理；
- 首要验收标准：一个 focused test、最小复现或明确的静态检查；
- 停止条件：达到范围、验收通过、证据不足需要回退诊断，或发现任务已升级为独立架构工作。

默认不启动子代理。只有在主代理按上述边界仍无法定位跨大量文件的问题时，才启动一个代理；代理提示必须写明目标、文件组、验收标准、排除项和停止条件。禁止同时启动多个代理，禁止让代理各自扫描同一仓库，禁止让有共享写入文件或互相依赖接口的任务并行。

代理或长命令出现以下任一情况就停止，不继续等待或追加范围：约 3 分钟没有有效工具调用或新证据；连续读取/搜索只重复已有信息；超出文件组、验收标准或授权；focused test 已显示失败来自测试夹具、环境或已有失败；需要设计新数据模型、跨层协议、事务/回滚或多个独立子系统。停止后由主代理保留已获得证据，重新缩小假设；不得把停止任务的方案或半成品写成已完成。

阶段闸门按以下顺序执行：

1. 先运行最小复现或 focused test，记录它是通过、失败、已有失败还是环境不可用；
2. 只修改当前文件组，并保持公共契约和用户未提交修改；
3. 重新运行 focused test；失败时停在当前阶段，不扩展功能或启动全量构建；
4. 只有 focused test 通过，才运行变更边界内的编译、集成或构建检查；
5. 只有本阶段验证通过，才开始下一个独立阶段，并重新记录目标、文件组和验收标准。

跨在线下载、分页、Web 桥接、AI 后端、数据库迁移、资源打包或设备回归等独立子系统的请求，必须拆成上述阶段。普通 Bug 修复不因后续架构愿景自动升级；若当前目标本身需要跨层协议或新数据模型，则先报告范围升级和新的结构授权边界。

## 完成状态

完成报告至少区分：

- `VERIFIED_COMPLETE`：实现已写入，首要验收和所需边界验证均有实际结果；
- `MODIFIED_UNVERIFIED`：已有修改但 focused test、构建或环境检查尚未证明；
- `DESIGN_OR_PARTIAL`：只有方案、接口草案、脚手架或部分实现；
- `NOT_STARTED`：本阶段尚未处理；
- `BLOCKED`：被已有失败、环境或缺少授权阻塞。

仅 `VERIFIED_COMPLETE` 可在摘要中写成“已完成”。其余状态必须列在“未完成与风险”中，并说明下一步所需的最小验证，不得用代理运行时间、读取量或设计完整度替代验证证据。


防止小文件累积出大上下文的字节级限制：

1. **单次读取**：Read 工具默认不超过 150 行或 15 KB（`max_lines=150, max_bytes=15360`）。大文件优先用 search_text 定位后分段读取，或用 `git blame` / `git log -- <path>` 聚焦历史。

2. **单次命令输出**：exec_command 默认 `max_output_bytes=8192, preview_bytes=4096`。需要完整输出时显式提高限制并说明原因。大输出优先重定向到文件（`cmd > out.log 2>&1`）再分段读取。

3. **累计工具输出**：单个任务的累计 Read + exec_command + search_text 输出达到约 40 KB 时，先总结当前发现和下一步计划，再继续后续批次。避免"读 12 个文件 + 跑 10 个命令"式的无节制累积。

4. **git diff 操作**：在大型或脏仓库中，MCP `git_diff` 工具可能返回不可控的大块输出。优先用 `git diff --stat -- <path>` 或 `git diff --shortstat` 获取变更摘要，仅在需要具体内容时用 `git diff -- <path> | head -n 100`。

5. **远程响应**：web_search 或 WebFetch 返回的 HTML/JSON 仅输出状态码、标题和不超过 4 KB 的已解压文本片段。禁止输出原始二进制、base64 编码或压缩字节流。

6. **二进制和压缩文件**：不对 `.gz`, `.zip`, `.tar`, `.png`, `.jpg`, `.pdf`, `.bin`, `.exe` 等执行 `cat` 或文本读取。需要内容时用专用工具（`tar -tzf`, `zipinfo`, `file`, `strings`）提取元数据或可读片段。

这些限制的目标是**让每个操作的成本可预测**，而不是在累积几十次"看起来正常"的操作后才发现上下文爆满。达到限制时，先用当前证据回答用户或给出中间结论，再决定是否需要继续调查。
