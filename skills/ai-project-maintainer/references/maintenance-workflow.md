# 维护工作流参考

## 两阶段读取协议

架构记录是定位工作的索引，不是逐文件读取清单。看到架构表中的模块、函数或目录，不代表要打开其中的所有源码。

### 阶段一：建立边界

在读取源码或执行递归搜索前，必须确定：

- `project_root`：用户提供的项目根目录，或由明确目标文件和最近的项目标记推导出的根目录。不能通过扫描当前工作区或父目录猜测。
- `target_anchor`：至少一个明确的文件、函数、类、路由、命令、配置键、错误文本、失败测试、堆栈位置或复现步骤。
- `scope`：包含目标的最小目录和直接项目边界。
- `exclusions`：`.git`、`node_modules`、`vendor`、`build`、`dist`、`out`、缓存、coverage、生成文件、二进制、媒体、`.env`、凭据、Cookie、Token 和无关 sibling 项目。

只读取控制面信息：

1. 从目标目录到确认的项目根目录之间的 `AGENTS.md`。
2. 优先读取项目根目录的 `ai-context/INDEX.md`。根据其任务映射，首轮最多跟进一个直接相关的架构主题和一个 Bug 主题；只有符号定位需要时才读取 `ai-context/FUNCTION_INDEX.md`。
3. 没有 `INDEX.md` 时，依次兼容 `ai-context/ARCHITECTURE.md` / `ai-context/BUG_HISTORY.md` 和根目录同名旧文档。长文档先定位标题并读取命中段落，只有索引不足且任务确实需要时才全文读取。
4. 根目录浅层列表，以及包管理、构建、测试和启动入口文件的名称或元数据。
5. 版本控制状态；不要因为状态检查而打开所有变更文件。

无法确定 `project_root` 或 `target_anchor` 时，向用户索取最小缺失信息；不要通过扫描工作区来猜测。

### 阶段二：按锚点读取

只有阶段一完成后，才读取：

1. 目标实现文件。
2. 为解释行为所需的目标一跳、自有调用方或被调用方。
3. 该路径实际使用的配置和数据结构。
4. 最小相关测试、复现脚本或错误堆栈指向的文件。

“直接依赖”严格表示目标路径需要的一跳项目自有代码，不表示目录或包内全部传递依赖。默认不读取标准库、第三方实现、生成代码和 vendor 文件。每读取一组文件后，重新判断是否确有证据需要扩大范围。

## 读取范围决策表

| 情况 | 阶段一先读 | 阶段二按需读 | 何时扩大范围 |
|---|---|---|---|
| 用户给出文件和函数 | 目标目录规则、`ai-context/INDEX.md`，必要时函数索引和一个主题 | 目标函数所在文件、一跳自有依赖、最小测试 | 当前路径无法解释行为或测试证明边界不完整 |
| 用户只描述现象 | 已确认项目根的规则、索引、入口元数据 | 精确错误文本/用户文案命中、入口、候选函数 | 存在多个真实调用路径或当前候选无法解释现象 |
| 测试失败 | 失败测试、规则、索引和测试配置元数据 | 被测函数、错误栈指向的一跳依赖 | 失败明确来自共享适配层、协议层或公共中间件 |
| 配置或环境问题 | 配置声明、启动入口、默认值位置 | 配置读取点和最小启动路径 | 配置存在明确覆盖层或由部署系统注入 |
| 模块抽离 | 原模块入口、索引、依赖边界和相关测试名称 | 原模块公共入口、迁移目标和直接消费者 | 需要迁移调用方、构建路径、启动路径或兼容入口 |
| 导入项目整理 | 顶层目录、入口/配置/包管理/测试命令名称、Git 状态 | 经用户同意后的迁移批次和受影响文件 | 只按已批准的迁移边界逐层展开 |

## 搜索闸门

每次搜索前写明搜索目的、已确认的 `project_root`、精确搜索词和预期命中类型。按以下顺序搜索：

1. 用户提供的精确路径。
2. 精确函数名、类名、路由名、命令名、配置键、事件名或错误文本。
3. 目标目录内的引用关系。
4. 只有一跳结果不足以解释行为时，扩大到所属 package。
5. 只有明确证据证明需要时，扩大到项目根目录。

默认限制：

- 单次搜索最多返回 50 个命中。
- 默认最多打开 12 个候选文件。
- 默认只追踪一跳调用或依赖关系。
- 达到限制时先收窄搜索词或路径，不能自动改为全仓扫描。

默认禁止：

- 从父 workspace 搜索普通维护任务。
- 首次使用 `config`、`error`、`handler`、`utils`、`import`、`data` 等泛化词。
- 使用无范围的 `rg ... .`、`find .` 或完整目录枚举后逐个打开结果。
- 搜索或读取依赖、构建输出、缓存、生成目录、vendor、二进制和秘密文件。
- 通过搜索所有同名文档决定适用规则。
- 未经证据递归追踪完整 import graph 或 call graph。

## 扩大范围条件

只有满足以下至少一项，才可从当前局部范围扩大：

- 精确符号存在多个实际调用路径，且当前路径无法解释现象。
- 一跳依赖跨越 package、进程、服务、数据库、文件、队列或浏览器边界。
- 测试失败来自共享适配层、协议层或公共中间件。
- 配置值存在多个明确覆盖层，或由部署环境注入。
- 修改涉及公共 API、schema、数据库结构、事件协议或共享数据结构。
- 模块抽离、移动或重命名需要确认所有导入方、入口、构建和测试路径。
- 当前测试或启动错误明确指向当前范围之外的文件。
- monorepo/workspace 配置明确证明另一个 package 是运行时消费者。
- 生成文件或 vendor 文件被运行时直接加载，且调用链已经提供具体文件证据。

扩大时必须：

1. 说明触发条件和新增边界。
2. 一次只扩大一层：目标目录 -> 所属 package -> 项目根目录。
3. 重新声明排除目录和搜索上限。
4. 记录新增文件及其必要性。
5. 若仍无法确定目标，向用户提问，不通过无限扩大搜索解决歧义。

完整项目扫描只在用户明确要求全仓审计、迁移盘点、依赖清查或类似任务时默认允许。普通 Bug 修复、局部功能修改和新项目初始化不自动触发完整扫描。

## 导入项目整理

“导入项目”“接手旧项目”“整理这个项目”与普通 Bug 修复不同：它可能移动文件、改变导入路径和启动方式，必须获得用户明确同意。

### 导入检查阶段（只读）

- 确认当前项目根目录，不把导入的已有项目当成新建项目。
- 只做阶段一的浅层地图：顶层目录、入口/配置/测试命令名称、包管理器元数据、启动命令、版本控制状态和现有项目记录。
- 不递归读取缓存、生成文件、依赖目录、vendor、sibling 项目和无关源码。
- 记录已有未提交修改和当前验证命令。

### 确认阶段

在移动、重命名文件或修改导入路径前询问：

```text
这是一个已导入的已有项目。是否要将它整理为便于维护的项目结构？
整理会移动或重命名部分文件并更新引用；我会先运行现有测试建立基线，再整理并重新测试。
选择“否”则保持当前结构，只进行普通维护。
```

没有明确同意就不整理。沉默、模糊答复或只说“先看看”不算同意。

### 同意后的验证闭环

1. 展示目标目录、迁移表、兼容入口和风险。
2. 创建 Git 分支或不覆盖的时间戳备份。
3. 运行整理前基线：测试、语法/类型、构建和启动冒烟；记录已有失败。
4. 在现有项目根目录内分批整理，不自动再套一层同名外部目录。
5. 更新导入、构建、启动和测试路径；保留兼容入口。
6. 运行同一套基线检查，再加受影响模块、导入路径和启动冒烟测试。
7. 对比前后结果，区分原有失败、整理引入的新失败和环境失败。
8. 验证失败时停止或恢复失败批次，不宣称整理完成。
9. 整理后更新架构说明；发现回归时记录 Bug 历史。

## 维护阶段

### 1. 建立局部模型

- 记录目标行为、复现步骤、期望结果和当前结果。
- 先确认 `project_root` 和 `target_anchor`，再按搜索闸门搜索符号、错误文本、路由、事件名或配置键。
- 确认入口、目标实现、返回值消费者和测试边界；默认只追踪一跳项目自有代码。
- 若有 `AGENTS.md`，只遵守目标到项目根路径上的更具体规则。

### 2. 形成假设

把假设写成可验证的句子，例如：“筛选发生在分页之后，导致类型字段在分页结果中被丢失。”列出支持证据和反证，不要把猜测写成事实。

### 3. 设计最小改动

优先级通常是：修复错误条件或数据边界 > 增加回归测试 > 更新必要的接口文档 > 其他改动。不要顺便格式化无关文件、升级依赖或重命名公共接口。

### 4. 验证

- 快速层：语法、类型、单元测试、目标模块测试。
- 集成层：相关 API、组件、数据库或文件流测试。
- 用户层：浏览器、设备、CLI 交互或截图复核。

只运行与变更风险匹配的层级，并在报告中区分已运行、未运行和环境不支持的检查。

### 5. 留痕

Bug 记录至少说明现象、根因、修改文件、修改方式、验证命令、结果和残余风险。优先追加到 `ai-context/bugs/` 的匹配主题并更新其 `INDEX.md`；旧项目沿用已有记录位置。结构变化再更新架构主题；普通局部修复无需制造架构噪音。

## 特殊边界

- **用户已有修改：** 先查看差异，分离自己的编辑范围，不覆盖或回滚。
- **备份：** 重构前使用 Git 分支或带时间戳的新备份路径，不覆盖已有备份。
- **外部动作：** 删除、推送、发布、发送数据、修改远端或生产环境前确认精确目标与范围；用户已明确授权的同一任务可以继续，但仍要检查最终目标。
- **凭据：** 不读取、输出或提交令牌、私钥、`.env` 中的秘密和浏览器凭据。
- **依赖：** 添加或升级依赖前说明版本、许可、供应链和锁文件影响；非必要不加依赖。
- **失败验证：** 保留失败输出的关键信息，不能把未解决问题写成已修复。

## 结束报告

```text
根因：用证据描述，不写未经验证的猜测。
修改：列出文件和函数，以及为什么需要改。
验证：列出命令和通过/失败/未运行状态。
记录：说明哪个 Bug/架构主题已更新，或为什么不需要更新。
风险：列出环境限制、未覆盖路径和后续建议。
```
