# 维护工作流参考

## 读取范围决策表

| 情况 | 先读什么 | 何时扩大范围 |
|---|---|---|
| 用户给出文件和函数 | 目标函数、直接调用、自定义数据结构、配置、最小测试 | 直接调用无法解释行为或测试证明边界不完整 |
| 用户只描述现象 | 搜索错误文本、用户可见文案、入口和候选函数 | 候选函数之间存在多个调用路径 |
| 测试失败 | 失败测试、被测函数、错误栈指向的直接依赖 | 失败来自共享适配层或外部协议 |
| 配置或环境问题 | 配置声明、读取点、默认值、最小启动命令 | 配置由多个层级覆盖或由部署系统注入 |
| 模块抽离 | 原模块公共入口、依赖边界、相关测试 | 需要迁移调用方或保留兼容入口 |

“直接依赖”指目标函数直接调用的自定义函数、读取的项目配置、使用的本地数据结构和被最小测试实际覆盖的适配器；第三方库只读所需 API，不要把整个依赖源码当作上下文。

## 维护阶段

### 1. 建立局部模型

- 记录目标行为、复现步骤、期望结果和当前结果。
- 搜索符号、错误文本、路由、事件名或配置键。
- 确认入口、目标实现、返回值消费者和测试边界。
- 若有 `AGENTS.md`，先遵守更具体的目录级规则。

### 2. 形成假设

把假设写成可验证的句子，例如：“筛选发生在分页之后，导致类型字段在分页结果中被丢失。”列出支持证据和反证，不要把猜测写成事实。

### 3. 设计最小改动

优先级通常是：修复错误条件或数据边界 > 增加回归测试 > 更新必要的接口文档 > 其他改动。不要顺便格式化无关文件、升级依赖或重命名公共接口。

### 4. 验证

- 快速层：语法、类型、单元测试、目标模块测试。
- 集成层：相关 API、组件、数据库或文件流测试。
- 用户层：浏览器、设备、CLI 交互或截图复核。

只运行与变更风险匹配的层级，并在报告中区分已运行、未运行和环境不支持的检查。

### 5. 留痕

Bug 记录至少说明现象、根因、修改文件、修改方式、验证命令、结果和残余风险。结构变化再更新架构说明；普通局部修复无需制造架构噪音。

## 特殊边界

- **用户已有修改：** 先查看差异，分离自己的编辑范围，不覆盖或回滚。
- **备份：** 重构前使用 Git 分支或带时间戳的新备份路径，不覆盖已有备份。
- **外部动作：** 删除、推送、发布、发送数据、修改远端或生产环境前确认精确目标与范围；用户已明确授权的同一任务可以继续，但仍要检查最终目标。
- **凭据：** 不读取、输出或提交令牌、私钥、`.env` 中的秘密和浏览器凭据。
- **依赖：** 添加或升级依赖前说明版本、许可、供应链和锁文件影响；非必要不加依赖。
- **失败验证：** 保留失败输出的关键信息，不能把未解决问题写成已修复。

## 结束报告

```text
根因：用证据描述，不写未经验证的猜测。
修改：列出文件和函数，以及为什么需要改。
验证：列出命令和通过/失败/未运行状态。
记录：说明 BUG_HISTORY.md、ARCHITECTURE.md 是否更新。
风险：列出环境限制、未覆盖路径和后续建议。
```
