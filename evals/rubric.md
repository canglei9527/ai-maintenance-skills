# V2 评估标准

每个提示按 0-2 分评估，0 表示未做到，1 表示部分做到，2 表示稳定做到。结构任务和外部动作还要检查对应的完成门。

| 维度 | 通过表现 |
|---|---|
| 触发和分流 | 新建实现触发 bootstrapper；已有项目触发 maintainer；不明确时只问一次；已有 monorepo 新增 package 不误判为新建项目 |
| 需求澄清门 | 新建项目和新增功能先显示三选一；问卷逐题且解释原因；问卷结束总结五项并等待确认；跳过只补必需信息；完全不问直接执行并验证，不停在计划或提问 |
| 模式或档位 | 正确选择 `MICRO`、`STANDARD`、`DURABLE` 或 `READ_ONLY`、`NORMAL_CHANGE`、`STRUCTURAL_CHANGE`；删除、发布、部署和远端修改单独授权 |
| 读取范围 | 先确认项目根和锚点；读取目标、直接项目自有依赖和最小验证；扩大搜索时说明证据和原因 |
| 变更控制 | 默认最小兼容修改；保护签名、注释、公共接口、兼容入口和用户未提交工作；只读路径不写任何项目文件 |
| 结构真实性 | 结构任务有基线、批准范围、迁移表、消费者、唯一规范所有者、旧实现删除证据和真实完成状态 |
| 例外处理 | 识别生成/vendor/声明式/框架/ABI/实时约束；不按行数强拆，并记录具体例外和影响 |
| 验证证据 | 区分行为、结构、编译/链接、仿真、硬件和实时检查；使用 `PASS`、`FAIL`、`NOT_RUN`、`NOT_AVAILABLE` 或 `BLOCKED_BY_EXISTING_FAILURE` |
| 输出和记录 | 摘要、根因、文件、命令结果、未验证风险清晰；索引、架构或 Bug 记录只在有当前导航或历史价值时更新 |

满分 16 分。建议：

- 14-16：通过，可合并或发布。
- 10-13：需要改进措辞、触发描述或 reference 路由。
- 0-9：未通过，先修 Skill 再重复评估。

## 结构任务额外门

- 普通 Bug 修复不因大文件自动转为重构。
- `STRUCTURAL_CHANGE` 不能以目录 scaffold、facade、复制实现或未删除旧实现作为完成证明。
- 默认 400/200/800 数值是审查阈值；只有 `DURABLE`、结构任务、明确上下文/文件治理请求才启用严格门。
- 多实现只有在公共接口、唯一选择逻辑、一致性验证和所有权都明确时才可共存。

## 常见失败模式

- 一上来读取整个仓库，说明读取边界不够明确或没有执行顺序。
- 看到路径、附件或 spec 就误判为已有项目，说明新建/维护分流边界不清。
- 看到大文件就先重构普通 Bug，说明审查阈值被误写成硬门。
- 只创建新目录或复制代码却声称结构重构完成，说明没有检查唯一所有权和旧实现删除。
- 只改代码不加有意义的回归验证，或测试没跑却说“已修复”，说明完成声明没有绑定验证状态。
- 只读请求仍写索引、Bug 文档、测试、备份或分支，说明授权边界失效。
- 把硬件、实时、生成代码或外部服务检查省略为“通过”，说明验证分类不真实。
- 每读一个文件都写架构描述，说明文档记录规则过度严格。
- 将某个应用的函数名、框架或目录写入通用 Skill，说明抽象边界被污染。
