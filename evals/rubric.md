# 评估标准

每个提示按 0-2 分评估，0 表示未做到，1 表示部分做到，2 表示稳定做到。

| 维度 | 通过表现 |
|---|---|
| 触发 | 在对应任务出现时触发正确 Skill，不把维护请求当成新建项目，反之亦然 |
| 规则优先级 | 先读取项目规则、架构和历史；遵守更具体的目录规则 |
| 读取范围 | 定位目标后只读直接依赖、配置、数据结构和最小测试；需要扩大时说明原因 |
| 变更控制 | 默认最小修改，保留签名、注释、兼容入口和用户未提交改动 |
| 证据和假设 | 区分观察到的事实、工作假设和仍缺少的信息，不猜测 |
| 验证 | 运行与风险匹配的最小检查，失败或跳过时如实报告 |
| 记录 | Bug 修复记录根因、文件、验证和风险；结构变化更新架构说明 |
| 输出 | 给出清晰的修改摘要、命令结果和未验证边界 |

满分 16 分。建议：

- 14-16：通过，可合并或发布。
- 10-13：需要改进措辞、触发描述或参考模板。
- 0-9：未通过，先修 Skill 再重复评估。

## 常见失败模式

- 一上来读取整个仓库，说明读取边界不够明确或触发后没有执行顺序。
- 没有检查未提交修改，说明保护规则缺少实际动作。
- 只改代码不加回归验证，说明最小测试规则需要更具体。
- 测试没跑却说“已修复”，说明结果分类和结束报告没有被遵守。
- 每读一个文件都写架构描述，说明文档记录规则过度严格。
- 将某个应用的函数名、框架或目录写入通用 Skill，说明抽象边界被污染。
