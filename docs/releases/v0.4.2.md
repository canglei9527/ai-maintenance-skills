# v0.4.2 发布介绍：检测累积性结构债务

发布日期：2026-08-12 · 版本线：0.4.1 → 0.4.2

## 一、这是什么项目

`ai-maintenance-skills` 是一套面向 **AI 维护**场景的项目技能包，包含两个互相配合的技能：

| 技能 | 职责 |
|---|---|
| **ai-project-maintainer** | 维护已有项目：解释、诊断、修复、重构、结构迁移。核心是四路分流：`READ_ONLY`（只读分析）/ `NORMAL_CHANGE`（最小修复）/ `STRUCTURAL_CHANGE`（结构迁移）/ `EXTERNAL_ACTION`（删除、推送、发布等外部动作独立授权门） |
| **ai-project-bootstrapper** | 新建独立项目：按 `MICRO / STANDARD / DURABLE` 三档初始化，落地模块所有权、任务地图、目录索引和低上下文读取路径 |

设计目标一句话：**让 AI 维护项目时读得少、改得准、改完有证据**。两个技能都采用"渐进披露"结构——`SKILL.md` 只保留路由和不可变规则，复杂规则按需加载到 `references/`，避免每次加载都烧掉大量上下文。

当前版本线：`0.1.0`（初版）→ `0.2.x`（安装/分流/导入整理）→ `0.3.0`（验证器与插件清单）→ `0.4.0`（低上下文门槛 + 可恢复发布自动化）→ `0.4.1`（V2 重构，四路分流 + 渐进披露）→ **`0.4.2`（本次）**。

## 二、v0.4.2 要解决的问题

### 现象：一个真实发生的失败案例

迭代 30+ 轮的 Flet 桌面应用，主文件 `aider_ui_flet.py` 长到约 2900 行。每次加功能都要同时改**控件构建、状态机、回调、语言词典、测试**五处——文件越来越大，改动越来越贵，最后成为典型的 **God Class**。

### 根因：增量补丁没有结构反馈回路

- 每轮请求都是"修复/加功能"这类收敛到具体行的指令，按 `NORMAL_CHANGE` 最小补丁处理是**正确响应**；
- 但"文件已 2900 行、五个职责混在一起"这条结构信息，被压成报告里的一句"记录文件大小风险"——**没有落到下一步行动上**；
- 于是下一轮继续打补丁，结构继续恶化，进入负循环。

**核心缺陷：技能知道"大文件是风险"，但不知道"何时必须停下来给结构方案"。**

### v0.4.2 的目标

1. 普通 Bug 修复**不被**强制扩大为重构（保留安全边界）；
2. 但结构债务**必须被看见、被具体化**——不允许一句"文件较大"就带过；
3. 用户明确要解决结构问题时，**直接进入结构路径**，不再用最小补丁 + "未来重构"空头承诺糊弄。

## 三、核心改动

### 1. 新增「维护性检查点」（Maintainability Checkpoint）

`NORMAL_CHANGE` 路径在完成前多一道检查。触发条件：

- 手写文件超过 **400 行**；
- 入口 / UI / 控制器 / facade 超过 **200 行**；
- 从 Git 证据可见**反复补丁历史**（多次最近提交都在扩展同一超大所有者）。

触发后检查 5 个结构信号：

1. 一个文件承载多个**独立变更原因**或多个用户工作流；
2. UI 构建、状态迁移、进程/持久化 I/O、解析、配置、本地化**混在一个类/模块**；
3. 同一功能需要**协同修改**控件、状态、回调、字符串、测试（同一个所有者）；
4. 顶层定义、公共入口、直接依赖形成了**可独立测试的分组**；
5. 最近提交或当前变更在**反复扩展同一超大所有者**。

**两个结果分支：**

- 信号全部不成立 → 报告"大文件但高内聚"并给出证据；
- 任一信号成立 → 报告 **`ACCUMULATING_STRUCTURAL_DEBT`**，并给出**具体责任图**：

```text
当前所有者 | 候选规范所有者 | 接口 | 消费者 | 独立验证 | 预期读取范围缩减
```

检查点是**建议性**的：聚焦修复照常完成，但结论不允许被降级成"文件较大"；只有当迁移未被请求时，才另行征求结构授权。

### 2. 结构意图识别：从措辞直接路由

以下用户语言现在被识别为**结构意图**，直接进入 `STRUCTURAL_CHANGE`，不再走最小补丁：

- 「让项目以后容易维护」
- 「解决 God Class」
- 「停止堆补丁」
- 「修复结构问题本身」

同时 `STRUCTURAL_CHANGE` 授权门做了微调：「容易维护」明确授权**在命名项目与兼容边界内的结构变更**；但删除、推送、发布、部署等破坏性/外部动作仍需独立授权——安全边界没有松动。

### 3. 结构路径增强：按「协调编辑簇」找职责

God Class 迁移不再只靠行数规划。基线阶段要求识别**哪些功能变更当前需要跨构建/状态/回调/字符串/I/O/测试协同修改**，把这些"编辑簇"转化为候选职责——行数只是线索，**编辑耦合才是迁移依据**。

### 4. 配套更新

- `SKILL.md` 描述扩展：`accumulating patches`、`oversized modules`、`God Classes`、`maintainability` 现在都是触发词；
- 不可变规则新增：*"聚焦补丁不能抹掉结构证据——在检查点区分内聚大文件与累积职责"*；
- 工作流第 5 步新增：`NORMAL_CHANGE` 完成前必须过维护性检查点；
- 评估用例新增 2 个场景 + 规则回归测试（见下节）。

## 四、评估与测试

### 新增评估场景（EVALS）

1. **Repeated Patches Grow A God Class**：提示词直接描述"2900 行 Flet 主文件、30 多轮迭代、每功能改五处、别再堆补丁"。期望行为：分类为 `STRUCTURAL_CHANGE`；按编辑簇而非行数识别职责；产出本地化/布局/会话状态/生命周期/编排的迁移表；一次迁移一个完整职责并删除旧实现；部分提取必须诚实上报。
2. **Focused Fix Encounters Accumulating Debt**：提示词是普通 bug 修复（"会话标题不刷新"），但目标文件混合五类职责且有补丁历史。期望行为：作为 `NORMAL_CHANGE` 完成修复、不强制迁移；完成前跑检查点；报告 `ACCUMULATING_STRUCTURAL_DEBT` 而非"文件较大"；给出具体责任图并另行征求迁移授权；不创建空重构标记、不把测试通过当可维护性证明。

### 回归测试

新增 `tests/skill-maintainability-routing.test.mjs`，锁定两条行为：① 明确的结构意图必须路由到 `STRUCTURAL_CHANGE`；② 聚焦修复保持有界、但必须保留累积债务检查点。连同既有门槛测试，**测试套件 14/14 通过**。

### 发布门自检

本次发布第一次被自己的验证器拦下：`verify-skill-repo.mjs` 要求 `fast-path.md` 保留原文短语 *"A 900-line target does not require a prior refactor"*（大文件普通修复规则），而新措辞把它改写掉了——**发布门精确地捕获了"安全规则被悄悄改写"的问题**。修正措辞后重新验证，**38 项仓库检查全部 PASS**。
