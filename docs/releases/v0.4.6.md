# v0.4.6 发布介绍：让最小改动服务于修复，不限制设计改进

发布日期：2026-08-24 · 版本线：0.4.5 → 0.4.6

## 一、这次发布解决什么问题

`ai-project-maintainer` 原本要求普通变更采用“最小兼容修改”。这条规则对修复 Bug、调整配置和处理局部行为问题是必要的：它可以防止 AI 借修 Bug 之机重命名无关代码、顺手重构整个模块，或者把用户没有授权的结构变化混进补丁。

但如果用户明确要求“界面现代化”“改进用户体验”或“优化交互流程”，同一条规则不能被机械套用。现代化不是换一套颜色，也不是给按钮增加动画；如果布局、信息层级、空间利用和主要交互路径都没有改变，用户真正指出的问题仍然存在。

本版本修正了这个边界：**最小改动约束 Bug 修复和配置调整，但不限制经过明确授权的设计改进。**

## 二、具体改动

### 1. 把普通变更拆成两类

`references/fast-path.md` 现在明确区分：

- **修复和配置调整**：继续做最小兼容修改，保持公共行为、命名和项目约定，避免无关重构。
- **设计改进和体验优化**：用户明确提出现代化界面、体验优化或交互重设计时，可以重新设计 UI 的布局、信息架构和交互模式。

### 2. 明确什么才算真正的界面现代化

设计改进可以包括：

- 重新安排信息层级和布局结构，例如把传统双栏改成更适合工作流的三栏或分区布局。
- 压缩工具栏和低频设置占用的空间，提高主要内容区的信息密度。
- 减少不必要的点击层级，让当前状态、预览和主要操作更容易被发现。
- 用字重、间距、分组和一致的控件层级表达视觉结构，而不是依赖大量颜色块、边框或装饰动画。
- 按主要用户流程重新组织 UI 组件，而不是只在原有布局上覆盖一层主题样式。

**只换主题颜色或添加动画，不能单独作为“现代化完成”的证据。**

### 3. 保留兼容性和验证边界

允许重新设计 UI，不等于可以随意破坏项目：

- 数据格式、API 契约和核心功能行为仍需保持兼容，除非用户明确批准改变它们。
- 需要区分行为验证、视觉验证和环境验证。
- 对有主要用户流程的界面改造，应通过运行应用、截图或人工交互检查布局、信息层级、溢出、可发现性和核心流程。
- 如果 UI 改造形成新的职责、公共入口或稳定工作流，仍需按结构变化规则更新索引和验证记录。

## 三、这对使用者意味着什么

- 报 Bug 时，AI 仍然应优先定位根因并做小范围修复，不会因为本版本而随意扩大修改。
- 说“把这个界面做得现代一点”时，AI 应先理解目标用户、主要工作流和当前布局问题，再提出或实施有实际影响的布局与交互改进。
- 如果用户只要求换色或调整视觉细节，仍可以做局部样式修改；但不能把局部样式修改包装成完整的现代化重设计。
- 设计改进的范围仍由用户授权决定。允许重做布局，不自动授权修改后端协议、数据模型或无关模块。

## 四、针对本次反例的验收标准

小说精校工具的现代化改造不能只检查主题色和按钮动画，还应至少回答：

1. 书籍、章节、正文预览和任务状态是否按工作流重新组织？
2. 顶部工具栏、空白区域和低频设置是否为主要内容让出了空间？
3. 用户能否更快找到当前章节、预览结果和下一步操作？
4. 深浅主题是否都保持克制、清晰和可读，而不是增加装饰噪声？
5. 主要操作、错误状态、加载状态和长文本是否经过实际窗口尺寸验证？

如果这些问题没有得到验证，仅凭换颜色和加动画不能报告“界面现代化完成”。
