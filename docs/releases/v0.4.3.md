# v0.4.3 发布介绍：测试分离 + Token 优化

发布日期：2026-08-13 · 版本线：0.4.2 → 0.4.3

## 一、这是什么项目

`ai-maintenance-skills` 是一套面向 **AI 维护**场景的项目技能包，包含两个互相配合的技能：

| 技能 | 职责 |
|---|---|
| **ai-project-maintainer** | 维护已有项目：解释、诊断、修复、重构、结构迁移。核心是四路分流：`READ_ONLY` / `NORMAL_CHANGE` / `STRUCTURAL_CHANGE` / `EXTERNAL_ACTION` |
| **ai-project-bootstrapper** | 新建独立项目：按 `MICRO / STANDARD / DURABLE` 三档初始化，落地模块所有权和最小可用结构 |

设计目标：**让 AI 维护项目时读得少、改得准、改完有证据**。两个技能都采用"渐进披露"结构——`SKILL.md` 只保留路由和不可变规则，复杂规则按需加载到 `references/`。

版本线：`0.1.0` → `0.2.x` → `0.3.0` → `0.4.0` → `0.4.1`（V2 重构）→ `0.4.2`（结构债务检测）→ **`0.4.3`（本次）**。

## 二、v0.4.3 解决的两个问题

### 问题 1：测试代码混在源码目录里

`scripts/` 目录同时放源码（`release.mjs`、`skill-frontmatter.mjs` 等）和测试（`release.test.mjs`、`skill-frontmatter.test.mjs`），一眼看不出哪些是生产代码、哪些是测试。随着脚本增多会越来越乱。

**解决：** 新建 `scripts/tests/` 子目录，所有测试文件移入其中，源码与测试分离。

### 问题 2：安装后不知道装了哪个版本

用户安装 Skill 后，没有任何方式知道当前装的是 `0.4.1` 还是 `0.4.2`。出了 Bug 也不知道该对照哪个版本的 CHANGELOG。

**解决：** `SKILL.md` 支持可选的 `version` 字段，frontmatter 解析器同步支持 `version: "x.y.z"` 格式。安装后检查 `SKILL.md` 即可知道版本。

## 三、Token 优化（约节省 15–18%，无行为变化）

### 为什么要做 Token 优化

AI 每次加载 Skill 都会消耗上下文窗口。references 文件里有几类明显的浪费：

| 问题类型 | 位置 | 浪费量 |
|---|---|---|
| TMS320/CCS 实时固件专用章节 | verification-and-safety.md + verification-and-exceptions.md | ~45 行 |
| 完成报告模板在多处重复 | fast-path.md 末尾 + SKILL.md | ~12 行 |
| 冗余章节（其他文件已覆盖） | structural-change.md + workflow.md + navigation-and-budgets.md | ~20 行 |
| 中英混写的章节标题 | 所有 references 文件 | ~8 行等效 |

**优化原则：只删冗余，不删规则。** 所有路由逻辑、操作路径、验证状态、anchor 字符串一律保留。

### 具体删除内容

**TMS320/CCS 章节（约 45 行）**

`verification-and-safety.md` 的 `Real-Time Verification` 章节和 `verification-and-exceptions.md` 的 `TMS320, CCS, And Real-Time Firmware` 章节，专门针对嵌入式实时固件（控制 ISR、ADC/PWM 链、CLA Task 等）。这两章对当前用户没有用，且已占 references 文件总量的约 15%。

**完成报告模板重复（12 行）**

`fast-path.md` 末尾有一个 `Completion Evidence` 代码块，内容与 `SKILL.md` 的完成报告格式完全相同。AI 加载 `fast-path.md` 时已经读过 `SKILL.md`，这 12 行纯属重复。

**冗余章节（约 20 行）**

- `structural-change.md` 的 `Large-File Normal Fix Boundary` 章节（5 行）：fast-path.md 的维护性检查点已完整覆盖，重复。
- `workflow.md` 的 `Current Records Only` 章节（7 行）：与 SKILL.md Immutable Rules 的内容重复。
- `navigation-and-budgets.md` 顶部 `Contents` 目录（8 行）：AI 不需要目录，直接读内容更快。

**中英混写统一**

所有章节标题和规则散文统一为中文。保留不变：英文代码标识符（`PASS`、`FAIL`、`NOT_RUN`、`NORMAL_CHANGE` 等）和仓库验证器要求的 anchor 字符串（`50 search hits`、`A 900-line target does not require a prior refactor`、`Migration Table` 等）。

### 优化结果

```
9 个文件修改：262 行插入，359 行删除，净减少 97 行
验证：node scripts/verify-skill-repo.mjs → 5 项全 PASS
测试：10/10 单元测试通过
行为：所有路由规则和操作路径保持完整
```

## 四、关于目录规模和超大文件的说明

这个问题值得单独说清楚。

### 当前目录结构是扁平的，不会随项目增长变成多级嵌套

```
skills/
  ai-project-maintainer/
    SKILL.md              ← 63 行，路由入口
    references/           ← 4 个文件，共约 213 行
  ai-project-bootstrapper/
    SKILL.md              ← 70 行，路由入口
    references/           ← 3 个文件，共约 159 行
scripts/
  *.mjs                   ← 6 个源文件
  tests/
    *.test.mjs            ← 2 个测试文件
```

这个仓库本身就是两个 Skill 的定义文件，不是一个会无限增长的应用。新增功能的方式是：修改或拆分 `references/` 里的 md 文件，而不是增加目录层级。最多再加1-2个 references 文件。

### 超大文件不会出现，因为有硬性上限

`verify-skill-repo.mjs` 在每次发布前都会检查：

```
SKILL.md <= 200 行
description <= 600 字符
body <= 14000 字符
```

超过就无法发布。这是防止 Skill 文件膨胀的强制门。

### 函数索引（FUNCTION_INDEX）不存在，也不需要

这个仓库没有 `FUNCTION_INDEX.md`，因为：
- `scripts/INDEX.md` 只是一个简单的脚本说明，几十行
- Skill 的"函数"就是 references 文件，直接从 SKILL.md 一跳可达，不需要额外索引
- 按需加载结构让 AI 不需要先读完整目录才能工作
